## Evidence and answer rules

- Use every asset's source files under `dataset/test-data/dataset/assets/<WELL_ID>/`, `fleet/users.json`, `fleet/areas.json`, well-type manuals and SOPs. Honor late `recorded_at` data by event dates, `type_history`, `team_history`, and `data_correction` notes. Don't equate a well's area team with its recorded well team when metadata says otherwise.
- Cite source record IDs and source document/report IDs near each finding. A maintenance record's `report_file` is authoritative for report prose; missing report text remains unknown. Retain authors, timestamps, original and corrected values, scope and conflict status for shared corrections/claims.
- A numeric value may be presented only when a source field or deterministic calculation supports it. `spill_est_volume_bbl` is spilled oil, not produced oil; line-pressure tests and allowable wellhead pressure are not reservoir pressure. Do not infer reservoir pressure or produced-oil volumes from status, temperature, spill volume, downtime, wellhead pressure limits or maintenance notes.
- For current production, apply the well's effective type manual to corrected wellhead-minus-ambient temperature. T200 threshold15°C, T35020°C, T50025°C. Apply OPS-3 note precedence: a later shut-in note means not producing; a later restart means producing-unconfirmed until an inspection confirms. Other operator notes do not set production status.
- Group the answer into factual values, evidence coverage/limitations and visual compliance. A correct block type alone is not a verified rendered UI. The run harness persists API answer IDs and typed UI blocks, but this plan does not authorize browser automation or claim screenshots.

## Exact question and session execution

The source of truth for request text and required visuals is `dataset/test-data/final-questions.md`. `experiments/06-evaluation/run_final_sessions.py` normalizes only markdown whitespace when checking hard-coded requests against that source. The plan requires21 turns/14 distinct API sessions: Q1–Q7, Q10 and Q11 are independent sessions (bounded concurrency2; Q7 turns remain sequential); Q8 is five sequential turns across four sessions; Q9 is six turns in one session after Q8. Q8/Q9 remain in question order so shared/private memory and in-session entity references have the intended chronology.

The actual session runner must preflight `/api/health` against the explicit expected test namespace/revision, verify Gemma model/provider/adapter and current test user profiles, then create and explicitly rename 14 backend sessions. It sends exactly one `/api/agent` SSE request per turn with `reference_date=2027-01-15`; it does not retry errors. It polls only persisted session history after a lost stream, saves every full answer envelope/UI block plus SSE terminal/stage receipts as per-turn JSON and Markdown, and records session IDs/profile names for the UI. No direct `CopilotService`, isolated fixture, browser automation or alternative model is used.

**Execution gate:** no live request until root supplies explicit GO with expected test namespace, dataset revision, server health readiness and approved command. Preserve previous sample-data report as earlier-revision evidence; never mix its counts/answers with this release.
