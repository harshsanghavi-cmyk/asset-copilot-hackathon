# How retrieval will answer contextual questions

17 Oct 2026 · concrete operating proposal before architecture approval · **not a working copilot or new model evaluation**. This contract aligns with the memory worker's `memory-operating-contract.md`, existing `integration-contracts.md`, the measured data audit and the exclusive Gemma policy. Its identical reader copy is `experiments/03-data-retrieval/retrieval-operating-contract.md`.

**Yes, SQL + FTS can support “what was the SOP we followed for that asset?” without embeddings.** The language model interprets the question; private conversation receipts identify “that asset”; SQL finds the relevant work and its explicit report links; indexed documents supply the rule text and recorded actions. FTS is lexical search, not a substitute for this context and join logic. The answer must distinguish **the prescribed procedure**, **what a report records**, and **whether the recorded evidence meets each requirement**. It cannot infer that a crew followed an SOP merely because that SOP applies to the well.

Only **Gemma 4 31B Instruct** may perform model work. The temporarily authorized route is `gemma-4-31b-it` through Google's compatible endpoint, governed by `agent-memory/model-policy.md` and the shared **30 RPM** cap. Existing generation/clean-JSON smoke evidence does not establish contextual retrieval quality or strict schema enforcement. **No API calls, installs, new experiments or application edits were made for this contract.**

**Latest USER content cap: 2K long-term TOTAL private + shared, 1K short-term user/assistant conversation including the rolling summary, and 2K retrieved context = 5K.** Persona/stage/tool instructions, current request, completion reserve and framing are separately measured overhead, not another concealed memory/evidence allowance. This replaces earlier larger budgets; targeted follow-up fetches replace evidence inside the 2K retrieval cap.

## Worked question: “what was the SOP we followed for that asset?”

The following illustrates the proposed runtime using actual source content. It is not a recorded copilot run, and these IDs belong only in examples/evaluation fixtures, never runtime routing rules.

1. **Resolve the user's reference before searching documents.** `read_context` looks up the active user's exact entity/event receipts and recent private conversation. A prior validated answer focused on WELL-0001 and the June spill can resolve to that well plus INS-0001-0185/MNT-0001-029. A summary saying “a troublesome well” is a pointer to expand, not authority to guess. If the user's prior receipt contains three wells or several incidents, return candidates and clarify which one. With no user-owned antecedent, say it is missing; never borrow another user's “we discussed” history. An explicit well ID supersedes a conversational guess.
2. **Establish incident, time and purpose.** If only the well is known, use `query_records` to list its relevant maintenance/incidents with dates and kinds. “Which procedure applied?” may be answerable for the type/current work category; “which did we follow?” needs an identifiable job/incident and evidence. Do not silently pick the latest repair when several are plausible. Preserve the conversation's explicit reference date and window; “we” does not prove the requesting user was a crew member.
3. **Resolve applicable rules.** Read asset metadata, type and applicable manual sections, plus the job's equipment and incident class. Follow explicit inheritance: T350 §6 refers maintenance escalation to T200 §10, while its production threshold is its own rule. Retrieve the cited protocol text, not only its title. Distinguish the original manual/SOP revision from a currently applicable attributed user override. The supplied documents identify revisions but do **not** provide complete historical effective-version intervals: say “the supplied revision states…” rather than assert which revision a crew had on the day. Missing version history stays explicit.
4. **Follow source joins for the actual work.** Use `maintenance.triggered_by_inspection_id`, `maintenance.report_file` and incident regulator links. For the June example the report is the unusually named `MNT-0001-june-2026-flowline-spill.md`, linked to MNT-0001-029; do not build a path from the job ID. Fetch its safety, testing, cleanup, compliance and relevant narrative sections. Bring current shared notes/corrections/conflicts into the same snapshot. An ordinary note without an inspection FK can still be relevant by asset/time/text, with that association labeled inferred.
5. **Compare recorded actions with prescribed duties.** The report records safety meeting, isolation, monitors, hot-work steps and pressure testing under WS protocols. It also records containment about **7 h** and written reporting after **41 h**, against supplied SR-02's **4 h** and SR-01's **24 h**. Those are different clocks from the repair's **35 h** duration. The report requests agency verification; cleanup and a request do not establish passing agency closure. Fetch all relevant regulator events before calling the current action closed. A later `closed` event does not prove the deadline was met.
6. **Answer with calibrated wording and citations.** A supported answer can say: “For the June flowline spill at WELL-0001, the report records work under the Field Work SOP and Spill Response SOP. It records several safety/testing steps as met, but containment and written reporting exceeded the supplied SR limits. Agency verification must be checked separately.” Cite the job/inspection, decisive report spans, the applicable SOP rows and any later event used. Say “the report records,” not “I verified the crew actually did this.” No actual source document records a universal “everything complied” fact.

Source examples: [June work report](/home/harshsanghavi/orca/projects/asset-copilot-hackathon/dataset/sample-data/assets/WELL-0001/maintenance-reports/MNT-0001-june-2026-flowline-spill.md), [Spill Response SOP](/home/harshsanghavi/orca/projects/asset-copilot-hackathon/dataset/sample-data/fleet/sops/spill-response-sop.md), [Field Work SOP](/home/harshsanghavi/orca/projects/asset-copilot-hackathon/dataset/sample-data/fleet/sops/field-work-sop.md), [T350 manual](/home/harshsanghavi/orca/projects/asset-copilot-hackathon/dataset/sample-data/fleet/well-types/T350.md). The actual report and SOP text were reread for this proposal. Their fictional rules govern the challenge; external legal standards do not replace them.

### Four separate evidence labels

| Label | Required evidence | Permitted conclusion |
|---|---|---|
| `prescribed` | Applicable versioned manual/SOP section, scope and any user override | “This requirement applies according to the supplied rule.” |
| `recorded_action` | Specific job/report/event span, with author/time and actual/planned qualifier | “The report records this step.” |
| `assessment` | Effective facts + applicable rule + deterministic comparison + coverage | Met, met late/breach supported, pending/not due, possible breach with no record, unknown, or not applicable |
| `unconfirmed_claim` | Attributed note/statement, conflict relationships and temporal association | “This person reports…, while this source disagrees.” |

No label automatically promotes another. The audit found 27 notes denying failure despite an associated repair diagnosing failure, another 30 different delay accounts, and nine interim reports with misleading past-tense summaries. Fetch surrounding status/qualifiers and retain both accounts instead of merging them into a fabricated cause or completed action.

## How paraphrases become retrievable

**Deterministic first.** Resolve names/IDs and relationship links; search report headings, protocol IDs and a small versioned synonym dictionary. Examples: “procedure” → SOP/protocol; “brought under control” → contained/containment; “soil specimens” → soil samples; “not producing” → temperature delta and the applicable type rule. These are search aids, not logical equivalences: a planned shut-in is context, not proof of the thermal state. FTS tokenization/stemming/phrase queries and BM25 rank are documented features; they do not understand arbitrary meaning. [SQLite FTS5 reference](https://www.sqlite.org/fts5.html)

**Optional Gemma assistance, UNTESTED.** In the existing planning call, Gemma may propose a small list of alternate terms, an intent, likely document kinds and named entities. Example proposal for the SOP question: `intent=compare_recorded_work_to_rules`, terms `["compliance check", "safety and permits", "spill response", "field work"]`, unknowns `["which incident?"]`. Validate terms against size/type rules; retain the original query. Gemma cannot select identity, expand permissions, replace exact entity/date filters, invent a protocol or declare a required source absent. An extra Gemma extraction call may propose a value only with an exact verifiable source span and an unknown option. Neither proposal is an embedding or a tested improvement.

**Search then expand context.** Filter by authorized dataset, resolved subjects, document kind and justified event dates; run escaped lexical terms; fetch an adjacent paragraph/section when a hit lacks a qualifier or table header. Report-only questions first enumerate linked reports from matching records, not document similarity. Do not overfilter broad discovery questions to a guessed asset/type. Search may discover candidate evidence; it cannot establish a negative fleet claim.

**Limitations and fallback.** Novel vocabulary, ambiguous pronouns, missing manual history, absent reports, inconsistent narratives and boilerplate competition remain real failure modes. Broaden deterministic terms or fetch the linked full section within budget; otherwise return supported facts with a missing-evidence statement, clarify the asset/event/meaning, or abstain. Do not call ordinary FTS “semantic retrieval” or claim that Gemma understands every context. A low score is not proof of absence; only complete structured enumeration can justify a scope-specific “none recorded,” and it still is not proof of real-world non-action.

## Four general capabilities, not a tool per question

These **four names are agreed with the memory worker**. Operations are small typed discriminated unions; they are not SQL strings, executable code or a concealed per-Q1…Q18 tool catalog. `ViewPlan` is validated chain output, not a fifth UI tool. General metric/grouping primitives can combine in new ways; unsupported operations produce a typed error/clarification rather than made-up SQL.

| Capability | Typed model-visible arguments | Server-owned behavior and typed result |
|---|---|---|
| `read_context` | `operation: resolve_reference | load | expand`, optional `reference_text`, known entity/fact handles, requested time overlap, opaque private-history cursor | Resolves exact directory IDs/candidates and **this user's** discussion receipts; loads bounded private continuity plus applicable shared operational claims/corrections/conflicts. Returns `resolved | ambiguous | absent`, candidates with source receipts, `ContextPack` handles/versions/token counts and scoped evidence. No arbitrary user, thread or namespace argument. |
| `query_records` | One allowed `collection`, entity refs, typed field/operator/value filters, allowed relation names, projection keys, metric definitions, group keys, order/rank and explicit time/as-of; bounded page request | Compiles approved primitives over effective records, applicable rules and validated joins. Returns immutable `ResultSet`, units/formulas/rules, complete population/unknown coverage, lineage manifest and presentation cursor. Also supplies job/report/evidence handles. Does not execute model SQL. |
| `read_evidence` | Selector union: `by_id` (validated handles), `related` (subject + evidence kinds), or `lexical` (term list + metadata filters); optional allowed neighbor expansion, bounded page/cursor | Resolves source registry IDs, exact links and manual inheritance or performs FTS. Returns original `EvidenceRef` spans, source/version/hash, prescribed/action/assertion distinction, match/extraction state, coverage/gaps and next cursor. Paths/URLs/raw byte ranges are not arbitrary model file-read inputs. |
| `write_knowledge` | Typed remembered-fact/note/correction/rule directive or validated draft handle, subject refs, proposed field/value or minimal statement, reason/validity, explicit supersession if supplied | Separate write validator enforces explicit user intent, scope/type/unit, existing value/conflicts, server author and expected revision/idempotency. Returns committed receipt/new revision or `needs_clarification | conflict | rejected`. Ordinary claims stay claims; never let the read compiler or formatting repair write a correction. Private facts remain private; domain facts can be shared without publishing surrounding chat. |

`query_records` has a **bounded general query algebra**: roots are assets/inspections/maintenance/regulator events, with a compiled relation catalog; metrics include count, sum and distinct counts on allowed fields plus reviewed domain derivations such as production/downtime/deadlines. Grouping allows validated asset/area/month/equipment dimensions. No arbitrary expressions, joins, field paths or callable function names come from Gemma. Exact rules still need deterministic implementation, but adding same-format wells/areas/reports does not add a tool or a hardcoded scenario answer.

The trusted gateway supplies dataset namespace, user/thread/exchange, authorization/audience, reference date, server committed knowledge head and pinned source revision. A model-supplied spoofed scope/author field is rejected. Every result/evidence follow-up reauthorizes opaque handles; possession of an ID is not access. Shared facts are not restricted to an author's team merely because a team owns the asset; the challenge shares domain knowledge across its users. Private receipts are a separate boundary.

Common read output fields: `run_id`, `dataset_revision`, `knowledge_revision`, normalized args/bounds/time basis, typed values/units, stable row/evidence IDs, source/rule/correction refs, `coverage`, `gaps[]`, `warnings[]`, `next_cursor`, and token/projection counts. Errors include `ambiguous_reference`, `absent_private_reference`, `unsupported_operation`, `invalid_scope`, `missing_rule_version`, `missing_report`, `unresolved_fact`, `resource_limit` and `stale_revision`. Error/partial status cannot masquerade as a successful zero result.

## SQL execution and correction safety

**Gemma proposes a plan; application code owns SQL.** Parse the closed JSON schema, validate metric/filter semantics, then compile allowlisted templates with bound data values. SQL identifiers/order/group keys are mapped from enums, not interpolated user strings. Join selection prevents cost/spill/fine multiplication across one-to-many children. Parameter placeholders protect values, not arbitrary SQL syntax or access policy. [Python DB-API binding and single-statement execution](https://docs.python.org/3/library/sqlite3.html#how-to-use-placeholders-to-bind-values-in-sql-queries)

The proposed read gateway has these independent controls; they are design requirements, not tested security guarantees:

- Open a server-configured DB path with SQLite URI **`mode=ro`**, and configure `query_only` as an additional guard. The model cannot select DB paths/URIs or change pragmas. `query_only` alone is not a complete read-only/security boundary. [SQLite URI modes](https://sqlite.org/uri.html), [query_only semantics](https://www.sqlite.org/pragma.html#pragma_query_only)
- Authorize the required schema/views, underlying tables and FTS shadow-table reads for approved templates only. Keep private-memory tables out of the general record-query connection; `read_context` uses its owner-filtered gateway. Fail closed on unknown tables, columns and functions. SQLite's authorizer can reject access during preparation; application scope checks remain mandatory. [SQLite authorization callback](https://www.sqlite.org/c3ref/set_authorizer.html)
- Allow only compiler-required operators/functions: e.g. count/sum/min/max, comparisons/CASE, approved date grouping, the latest-row window operation and supported FTS MATCH/BM25/snippet calls. Explicitly prohibit model-controlled SQL text, raw WHERE clauses, recursive CTEs, cross joins, DDL/DML, ATTACH/DETACH, arbitrary PRAGMAs, extension loading and filesystem/network/side-effect UDFs. Do not expose `readfile`, `writefile`, `load_extension`, shell or HTTP operations. Registered source IDs resolve through an allowed viewer/registry; source reading is not arbitrary file access.
- Execute a single prepared statement per compiler step. A controlled transaction may contain several application-generated statements, but never run a model script or `executescript` on model content. Escape/tokenize the FTS term list separately from SQL binding; reject raw FTS operators/wildcard expressions outside the small allowed query grammar. [Python sqlite3 execution contract](https://docs.python.org/3/library/sqlite3.html#sqlite3.Cursor.execute)
- Enforce dataset and user/audience predicates from trusted context on initial query, cache lookup, cursor continuation and evidence fetch. Read-only SQL alone does not prevent information leakage. Bind one short snapshot, materialize results, then close it before model/network calls. Check committed head when publishing; recompute affected results or label the complete answer historical if it advanced. Never mix corrected and old panel values.
- Apply resource limits and a progress/deadline cancellation handler. A nonzero SQLite progress callback can interrupt a running query; runtime limits constrain supported statement dimensions. These are useful mechanisms, not a guarantee that an arbitrary generated query is safe. [Progress handler](https://www.sqlite.org/c3ref/progress_handler.html), [SQLite limits](https://www.sqlite.org/limits.html)

**Proposed initial interactive limits** (tune with actual load; not benchmarked acceptance constants): at most 8 read-tool calls in two evidence rounds; up to 4 compiler statements per `query_records` call; at most 3 approved relation edges, 16 projected columns, 2 grouping dimensions and 120 time bins. Maximum 100 displayed result rows/page, 16 evidence handles/fetch, initial lexical top-8 expanding to at most 16 candidates in round two, 12 search terms of at most 64 characters each; no unrestricted prefix query. Reject excessive plan/string/expression sizes before preparing SQL.

Use a **2 s statement deadline**, **5 s composite query-call deadline** and approximately **5 million VM-instruction budget**, checked every 1,000 VM operations; add a bounded worker-memory/result-materialization cap (initial proposal 128 MiB per result spool). Reject a plan whose validated estimated fanout exceeds one million intermediate rows; estimation is admission control, not a claimed exact SQLite row-counter guarantee. Scope may be the full supplied history, whose min/max dates are explicit in the manifest; never invent a shorter default window to satisfy a limit. Too many bins/records means request a coarser presentation, chunk a complete calculation under a larger authorized job, or return a clear resource-limit result. An interrupted calculation has unknown total/coverage unless separately established; it is not a valid partial sum presented as the fleet total.

**Pagination limits display, not aggregate input.** A fleet sum/count/ranking processes all matching effective records before output ranking/pagination; the 100-row page limit and top-8 passage limit never sit upstream of that calculation. Exact membership evidence stays in a retrievable manifest even if only a few rows reach the prompt. Write corrections through a different owned connection/transaction: validate the target/current effective value, scope/validity/author, compare expected revision, append original and replacement with reason, commit idempotently, increment knowledge revision and emit invalidation/outbox. No arbitrary SQL is accepted there either; save acknowledgements require a durable receipt.

**The user's content limit is 5,000 tokens: long-term 2,000 + short-term 1,000 + retrieved context 2,000.** Internal splits are proposed, unmeasured settings; these are not database-size or SQL-population limits. There is no automatic larger envelope behind this budget.

|---|---:|---|

Already admitted shared claims/corrections/rule cards appear once in the shared 1K long-term slot. Result/source references can point to those cards, but the retrieved 2K does not repeat their full text as another allowance. A result may necessarily include an effective corrected value and citation reference; it does not need the correction narrative twice. Newly fetched SOP/report prose stays retrieved context, not relabeled shared memory to escape the cap. Count repeated serialized reference metadata wherever it occurs.

Unused subslots may be pooled inside each fixed 2K/1K/2K category, without silently borrowing across the three caps. Preserve contradictory claims, correction provenance, rule qualifiers and coverage. Five-panel answers reference server-owned data instead of sending every chart array through Gemma. **SQL still processes every matching record before aggregation**: the supplied 39,567 inspection rows can produce concise totals and lineage handles without loading those rows into the prompt.

Separately disclose compact persona/trusted-routing instructions `P`, stage/tool instructions `T`, the current request `U`, transport framing `F`, explicit completion reserve `O` and safety `H`. Actual model input is `content <=5,000 + P + T + U + F`; provider-window accounting adds `O + H`. Those actual serialized sizes must be counted, not assumed zero or inflated into a hidden memory allowance. Only the current submitted user request belongs in U; historical dialogue remains inside 1K. Tool payload facts belong inside retrieved context, never an unmetered framework message history. No fixed larger total replaces the user's cap.

The private long-term archive slot is for durable atomic facts and selected entity/event receipt details. Historical user/assistant excerpts retrieved by `read_context` still count inside short-term1K, rather than being relabeled long-term or evidence. Attribution/citation metadata carrying domain content remains in its content slot; framing overhead is not a place to hide source text.

**Is 2K evidence enough?** It can be enough for a targeted asset/incident question: exact SQL computes the answer, then the prompt contains decisive rows, relevant rule/report excerpts and coverage. It is not a proven universal allowance for broad or conflict-heavy explanations. Fetch the exact supporting section/neighbor and **replace** less relevant evidence inside 2K; a second round cannot append another hidden 2K. If all indispensable evidence still cannot fit, return a supported partial answer, narrow/clarify the incident or abstain on that part. Do not increase the limit silently, drop required qualifiers or claim full support from omitted evidence.

## Bounded evidence loop and stopping rules

**Normal path:** user-owned reference resolution → typed query plan → complete effective-record queries/direct rule/report retrieval → coverage check → evidence pack → Gemma explanation/ViewPlan → local validation/publication. Rules and formal corrections apply inside tools even when no model asks to retrieve them.

**One follow-up evidence round** is allowed when a named gap can be closed: missing type/inherited rule; source hit needs adjacent section; referenced report has not been loaded; conflicting action/closure evidence; unknown field extraction; ambiguous entity resolved by an exact directory lookup. Fetch the missing source instead of asking Gemma to reason longer over the same incomplete excerpts. Recompute derived classifications/deadlines when corrected values change. A full-scope report analysis enumerates/extracts every linked candidate locally; it does not send every report to Gemma one by one.

After two rounds, stop if the reference remains ambiguous, the required source/version is absent, conflict cannot be resolved, the operation is unsupported, computation was interrupted or evidence cannot fit. Return supported portions plus explicit gaps/coverage, or a focused clarification. A ranked search can always return something irrelevant, so “we got eight hits” is never the stopping criterion for a proof.

Proposed foreground model-call bound: normally **one planner + one composer**. At most one additional evidence-stage Gemma assistance call (a replan **or** extraction, not an automatic per-report loop) and one formatting repair give **four completion attempts maximum**. Query terms proposed inside the first planner do not require a separate call but remain quality-untested. Deterministic follow-up fetches do not themselves need another model. Provider errors and budget exhaustion are explicit states; no retry storm or alternate model. Background memory work shares the same global limiter and has its own durable scheduling policy from the memory contract.
