## Recommendation for coordinator synthesis

Adopt **application-owned relational authority and memory records, a bounded LangGraph workflow with durable checkpoints, and an authorized shared-knowledge gateway that combines exact subject lookup with prose retrieval**. Keep private preferences/capsules and exact discussion entity sets separate from shared operational knowledge. A normal asset question must consult applicable shared notes as well as corrected measurements and rules, regardless of vector relevance. A domain fact remembered by A is stored once in shared knowledge and read by authorized B; it is not copied into A's private profile and hoped to reappear.

This improves the initial recommendation without rejecting its strongest parts. SQLite + FTS5 remains a credible local storage choice; LangGraph is a workflow choice compatible with it. I favor LangGraph for the intended composable workflow because resumable evidence gathering, correction receipts, bounded repair, compaction and partial dashboard delivery create useful explicit boundaries. The actual restart/replay slice passed, but the explicit journal matched it; this preference is architectural judgment, not a measured superiority claim. Keep the proven application-owned authority/scope contracts whichever workflow is selected.

**Measured update:** the explicit journal and actual LangGraph/SqliteSaver workflow each pass **53/53 identical fixed-proposal state checks**. Synchronous LangGraph checkpoint durability was necessary for the tested snapshot-retention guarantee under forced process exit; both approaches still require application write idempotency. A fresh gbrain PGLite engine passes **17/17 exact shared-projection integration checks**. These results establish a state-behavior tie for the tested small workflow and credible gbrain engine integration, not semantic/answer superiority. LangGraph remains an architectural preference for richer resumable workflows; the explicit journal is a demonstrated alternative, and no winner should be forced from this suite.

The compared architecture shortlist is **H1**, relational authority/private receipts/shared claims + LangGraph + exact/FTS retrieval, and **H2**, identical authority/workflow/private memory + a pinned gbrain sourced shared-knowledge adjunct. H2 remains a contender for broader organizational prose and relationship recall under an eligible Gemma-only/deterministic configuration. Its current explicit `remember`, sourced retrieval and bounded `context_pack` materially exceed a simple vector cache, but only its exact engine projection was exercised here. Neither hybrid's semantic or live-model answer quality was measured. Select H1 for the current plan's core path; retain H2 as an extension requiring demonstrated benefit, not because fewer dependencies are inherently better.

Retain the existing `EvidenceRef`, `ResultSet`, `ViewPlan` and `AnswerEnvelope` seams in [integration-contracts.md](integration-contracts.md). Amend them with explicit audience/subject distinctions, shared operational-claim retrieval, index watermarks, typed conflicts and snapshot publication rules below. Keep Gemma as the exclusive runtime model and local output validation; provider/API verification belongs to the coordinator and every optional extractor still needs a compatible Gemma-only configuration.

## What the initial tracks get right, and what changes

The memory track already correctly separates summaries, private entity receipts, corrections, type rules and ordinary claims. The retrieval track correctly rejects top-k totals and follows linked reports. The UI track correctly separates AG-UI transport from trusted visual components and shared result references. This review does not claim these capabilities were absent.

Four seams still materially change the design:

1. **Shared remembered knowledge needs an explicit product path.** A correction ledger alone does not answer “what did our team learn about this equipment?” Add asset/type/equipment/team/organization assertions, hypotheses, plans and guidance, with shared visibility and evidence, independently of correction authority. Existing diagrams overemphasize private capsules and show shared notes primarily behind the calculation tool.
2. **Audience, subject and authority are different fields.** A team-authored rule can target every T350 well and be visible organization-wide. A shared namespace does not authorize a read. An asset mention in a private episode does not authorize publishing that episode.
3. **Revision consistency must be enforceable, not a label.** A claimed revision on five independently executed queries does not make them a snapshot. Index lag, fresh users without a client watermark, checkpoint replay and publication races need concrete handling.
4. **Complete evidence retrieval differs from search.** “Which spills were late to contain?” requires all candidate spills and all linked reports in scope, plus extraction coverage. A semantic hit can locate a cause; it cannot prove there are no other failures or that the hit caused observed downtime.

## Knowledge and memory layers

| Layer | What is durable | Read path | What it may change |
|---|---|---|---|
| Immutable source registry | Raw records, manuals/SOPs, linked report content, hashes, spans and dataset lineage | Exact IDs/joins; scoped section search | Evidence only; raw files remain unchanged |
| Structured authority ledger | Accepted field corrections and scoped rule overrides, originals, previous effective values, authors, reasons, validity and supersession | Mandatory effective-record/rule evaluation | Effective values, classifications, aggregates and deadlines |
| Shared operational claims | Attributed plans, observations, domain facts, equipment/team/org guidance, hypotheses and conflicts | Exact subject/audience/time lookup first; lexical/semantic expansion second | Context/explanations; never raw measurements or formal rules merely by insertion |
| Private durable facts | Explicitly remembered preferences and work context; validated useful extractions | Active user's bounded always-loaded capsule plus exact/archive expansion | Personalization, never another user's state or asset truth |
| Private episodic/entity receipts | Ordered well IDs from actual validated answers; intent, bounds, run/exchange and date | Exact user-owned lookup before semantic fallback | Resolution of “the three wells”; values are recomputed |
| Thread working state | Recent exchanges, summary versions, unresolved references, run state and tool receipts | Owner-checked thread checkpoint and summary | Conversation continuity and recovery |
| Retrieval projections | FTS chunks, optional embeddings/graph edges/cards and compressed capsules | Authorized adapter with revision/coverage check | Candidate discovery; rebuildable from canonical evidence |

**Core memory:** always load read-only persona/routing, active identity, reference-date rules, the active user's durable compact fact capsule and a small organization context header/knowledge manifest. Curated organization essentials can be pinned; the full fleet's plans, corrections and raw claims cannot be in every prompt. Load relevant shared subject cards after resolving assets/type/team, and apply corrections/rules inside tools regardless of prompt budgets. For “what should I know?” with no subject, search authorized organization/team updates, disclose bounded coverage, and offer drill-down. Empty context must not mean “there is no shared knowledge.”

The existing 3K versus 5K loaded-memory trial is reasonable but unmeasured. Keep its capsule, summary, recent-tail and archive allocations; give fresh shared query evidence a separate bounded allocation. Do not silently fund more private context by omitting shared conflicts. A capsule manifest is not equivalent to all original facts being in context: show that details require expansion, preserve every raw fact, and measure expansion success.

### Canonical representation and authority

Use flexible prose alongside normalized fields; do not require every operational sentence to fit a rigid oil-field predicate catalog. Proposed canonical fields are `knowledge_id`, organization/dataset namespace, `audience_kind/audience_id`, `subject_kind/subject_ids`, optional predicate/object/unit, minimal statement, `kind`, assertion status, `content_origin`, source IDs/spans, author, `recorded_at`, world-valid interval/precision, version/revision, extraction version and `supersedes/conflicts_with` links. A private statement's source-message link is internal; shared evidence resolves a separately stored minimal domain assertion with attribution.

Separate at least three status axes: **extraction fidelity** (does the candidate match the source?), **assertion state** (reported/hypothesis/disputed/withdrawn/confirmed by cited evidence), and **authority state** (ordinary claim/accepted formal correction/active user rule). A high extraction score says nothing about whether the speaker was right. No confident wording, repeated claim, semantic similarity or LLM summary can promote a claim to a formal correction.

One organization/dataset can contain all challenge users with access to shared operational facts; the demo picker identifies the active person. Do not infer access restrictions from `team_id`: Q16 deliberately shares Jake's planned work with Michael across teams. Subject team, author team and audience team are distinct. For future restricted deployments, authorization intersects authenticated membership, explicit audience grants and source visibility before any prompt, index search, source viewer, cache, stream or replay. The model never supplies user identity or expands a namespace. Postgres RLS can add defense in depth, but policies must account for owner/superuser bypass; SQLite requires server-enforced query boundaries. [Postgres row-security semantics](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

## Exactly how “remember that” is scoped and saved

| Input/intent | Storage and acknowledgment | Clarification boundary |
|---|---|---|
| “Remember that WELL-0007 has planned work from 17 Oct for ten days” | Minimal organization-shared asset claim; synchronous durable save; show subject, approximate period and author | No generic approval: operational sharing is a stated feature. Ask only if asset/date meaning is unresolved |
| “FYI for everyone…” | Same shared path with explicit audience intent | No repeated confirmation |
| “Remember I prefer tables” | Private fact and refreshed capsule for this user | None unless the preference contradicts another explicit current preference |
| “Remember the three wells we just discussed” | Private entity-set receipt linked to that answer | Ask if multiple recent sets are equally plausible |
| “Remember that” after a mixed personal/domain exchange | Resolve exact referenced statement first; split minimal domain claim from personal context where clear | One focused question if the antecedent or desired audience remains ambiguous |
| “Keep this private: I suspect WELL-X has a seal issue” | Private hypothesis; no automatic shared projection | Respect explicit privacy. Saving privately does not make it a fleet correction |
| “The reading was wrong; the re-measured value is…” | Structured correction transaction against identified observation/field; preserve reason and originals | Missing target/value needs clarification; Q12's conflicting inspector note is disclosed after the clear correction applies |
| “For all T350 wells use two corrective pump-jack repairs…” | Typed user override with type, equipment, count/lookback, evaluation validity and author | No blanket approval if intent/scope is clear; unresolved policy target needs clarification |
| Ordinary domain assertion without “remember” | Useful unambiguous assertions become attributed shared claim candidates through automatic extraction under the visible operational-sharing policy | Do not ask about every statement; retain hypotheses/negation and hold ambiguous/sensitive candidates privately pending scope resolution |

Do not publish the whole message to obtain cross-user memory. “I am worried about my review; remember WELL-X has work planned” shares only the operational plan. A user saying “A colleague claims X” is a report of a claim, not direct confirmation by that colleague. Questions, hypotheticals, retracted text and assistant speculation are not new asserted truth. If the user explicitly saves a past calculated answer, preserve a historical receipt with its revision/date; do not insert a timeless shared fact.

**Explicit saves are synchronous.** Resolve antecedent/entities/time → classify private/shared and claim/correction/rule → authorize audience and target → validate source span and type → inspect conflicts → commit → acknowledge exact receipt. A failed extraction or malformed JSON cannot yield “saved.” Writes use their own idempotency key and are never reissued by output-format repair.

**Automatic extraction is a separate path.** After the raw exchange/receipts are durable, enqueue a source-ID-keyed job. Extract useful atomic candidates from user assertions and validated entity receipts; preserve source modality, negation, approximate time, epistemic wording and speaker attribution. Check schema, known IDs, supported source spans and audience policy before admission. Ambiguous entity/date/scope stays a candidate; an unsupported source is rejected. Automatic extraction cannot create formal corrections/rules or relax system policy. Explicit feedback can use extraction to parse a draft, but its clear user intent and typed validation authorize the formal path. Surface a pending/save receipt when relevant; background completion is not immediate durability.

Before B answers about a subject, process pending earlier extraction jobs for that subject or disclose pending context and consult authorized minimal source assertions through a bounded reconciliation step. Otherwise “we extract asynchronously” creates an unnoticed cross-user visibility gap. Explicit A→B benchmark cases must not depend on a background worker happening to finish in time. Rebuildable search indexing can remain asynchronous because exact shared lookup is immediate.

## Shared write/read path and consistency

Proposed application gateway:

```text
remember(context, source_message_id, resolved_antecedent, typed_intent)
  -> commit receipt {knowledge_id, kind, audience, subjects, valid_time,
                     assertion_status, authority_status, knowledge_revision}

load_context(context, query, resolved_subjects, budget)
  -> own_core/capsule, own_summary/tail, own_entity_receipts,
     applicable_shared_claims/conflicts, rule/correction_refs,
     evidence refs, observed_head, retrieval_watermark, coverage

query_domain(context, typed_query, snapshot)
  -> ResultSet at the same dataset_revision/knowledge_revision
```

The coordinator's `expected_revision` contract needs both conflict detection and throughput. In one short write transaction, compare expected effective **target versions** (or revalidate the global revision read set), append a change, update its projection, advance the organization/dataset `knowledge_revision`, store idempotent receipt and append an outbox event. Disjoint changes can serialize and revalidate without asking either user. Competing same-field/interval corrections need conflict resolution rather than last-write-wins. A stale global revision caused by an unrelated well is a mechanical retry, not a reason to ask the user again.

The outbox makes commit and eventual invalidation delivery durable; a push notification itself is not part of a database transaction. Initial cache invalidation can conservatively invalidate all results at an older knowledge revision. Later dependency indexes can invalidate narrower subject/rule populations, including newly matching type members. Semantic adapters record `indexed_through_revision`; missing or older coverage cannot certify absence. Fetch the canonical changed claims since that watermark and union/deduplicate authorized candidates; validate supersession/eligibility against the current ledger. Thus stale vector text cannot resurrect a withdrawn claim.

**Every request reads the server's committed head**, including B's first request; do not rely only on a client-supplied `minimum_knowledge_revision` from A's receipt. Cache keys include organization/dataset lineage and revisions, authorization/membership version, user for private results, private memory version, normalized query/window, tool/prompt version and evidence/index version where relevant. Exact totals remain independent of index version. Result/evidence fetches reauthorize IDs; shared raw-query caches may be shared only if their inputs/results contain no private context.

For a multi-tool answer, materialize results in a short consistent database read snapshot, or explicitly evaluate immutable source plus versioned overlays at revision R. Do not hold a SQL transaction open across model network calls. Persist result sets and their manifest at R. At publication, compare the head in the same short transaction that stores the answer receipt. If changed, recompute affected panels/narrative or publish the **whole** answer as a historical snapshot. A correction arriving after publication marks that answer stale through the outbox; there is no physical guarantee that a display is forever the newest state. Current dashboards stage replacement results and atomically swap all affected panels and narrative to R+1; historical chat messages retain their original as-of label and refresh action.

SQLite WAL readers can keep seeing their older transaction snapshot after a writer commits, and SQLite has one writer at a time. This is useful for short coherent reads but does not justify treating a long-lived connection/transaction as current after a correction. Fresh reads must start after the commit; retry busy/snapshot conflicts with stable write identity. Move to Postgres for multiple API replicas, sustained simultaneous writes or stronger deployment/authorization needs, rather than assuming 200 wells requires it. [SQLite isolation](https://www.sqlite.org/isolation.html)

### Temporal validity, contradictions and supersession

Keep world time separate from when the system learned the statement. A correction learned on 17 Oct can change the effective value of the 15 Oct observation used in a 16 Oct scenario. “What do we know now about then?” uses latest accepted corrections; “what did we know then?” also restricts transaction time. Reference date and query window are explicit; neither is silently replaced by the workstation clock.

A ten-day workover plan from 17 Oct has an approximate planned interval, not proof of an actual shutdown or restart. Preserve day precision and wording. By 28 Oct it is a historical plan whose completion is unknown unless a new source says otherwise. A prospective plan is already known before its scheduled start, so “any downtime planned?” searches plans by occurrence interval as well as active assertions. Do not filter it away merely because it is not occurring today.

A T350 rule “now” applies to evaluations from the active reference date until superseded, with a disclosed assumed validity if no end was given. Its 12-month repair lookback still includes earlier repairs. Historical event applicability is a separate rule field if explicitly requested. A type predicate is evaluated against dataset membership, not a frozen list of sample IDs. The manual remains original evidence and the override remains Michael's rule.

Store conflicts as relationships between claims about the same predicate/subject and overlapping intervals, preserving evidence and author. New unrelated time intervals can coexist. The same assertion repeated by one source is not independent corroboration. Duplicate delivery is idempotent; identical claims from different authors retain distinct provenance. Semantic deduplication must not merge opposite values or join private records across users.

First clear formal corrections apply immediately while inconsistent ordinary notes remain visible (Q12). Two conflicting formal corrections without explicit supersession preserve the existing accepted effective value, mark the new correction unresolved and ask the necessary reconciliation question. A later “replace my earlier correction X with Y” can explicitly supersede it when authorized. Retraction withdraws active use, not history. Deleting a private preference does not revoke an independently shared operational correction.

## Meaningful hybrid comparison: documented interfaces and limits

All candidates below retain immutable sources, relational effective queries, typed correction/rule authority, exact private entity receipts and application authorization. The comparison is about where workflow state and semantic knowledge live. No product is credited with our domain semantics merely because it offers memory.

### H1: relational authority + bounded LangGraph checkpoints/store adapter

Official APIs distinguish `builder.compile(checkpointer=..., store=...)`, thread configuration via `thread_id`, and a runtime context separate from model messages. Long-term store operations include exact `aget(namespace,key)`, overwriting `aput`, and prefix-scoped `asearch(..., query, filter, limit, offset)`. Namespaces can represent shared organization knowledge and private users. These are storage interfaces, not an authorization policy. [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence), [store interface](https://docs.langchain.com/oss/python/langgraph/stores), [runtime example](https://docs.langchain.com/oss/python/langgraph/add-memory)

Proposed graph: resolve context → classify intent → optional typed commit → exact/linked evidence → optional exploratory retrieval → compose/view plan → validate → persist/publish; compaction is a separate durable job. Keep graph step limits and one formatting-repair edge. Bind opaque thread IDs to owners in application tables. Authorize checkpoint history/time-travel/resume, not just new requests.

Checkpointers persist successful pending node writes within a failed super-step, reducing repeated successful work on resume. That does **not** establish an atomic transaction with an external application ledger. A crash after correction commit but before checkpoint persistence can replay the node. Retrieve the idempotent commit receipt on replay, then revalidate current knowledge revision before composing. [Checkpointer behavior](https://docs.langchain.com/oss/python/langgraph/checkpointers)

Use application relational records as memory source of truth and optionally expose a restricted `BaseStore` adapter/projection. Do not duplicate accepted corrections into a second freely writable KV authority. Standard `PutOp` supplies value/index/TTL but no application target-version compare-and-swap; implement that at the ledger seam. Prefix searches can span child scopes, so do not expose arbitrary prefixes, particularly the root tuple. [Actual BaseStore/PutOp source](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint/langgraph/store/base/__init__.py)

**Disqualifier:** if the pinned durable adapter cannot pass replay/ownership tests or adds more recovery code than the plain journal control, use that control while retaining identical memory contracts. In-memory checkpoint/store examples cannot satisfy restart acceptance. For local SQLite, verify the selected adapter availability rather than assuming its store package matches the checkpoint package; a direct application memory gateway is sufficient initially.

### H-Letta: relational authority + per-user Letta agents + shared blocks/archive

The legacy V1 API can `client.blocks.create(...)`, attach the same `block.id` using `block_ids`/`client.agents.blocks.attach`, and update its `value`. Blocks are always in context and can be read-only. Concurrent whole-value updates are explicitly last-write-wins. A real hybrid can publish a small application-generated shared organization capsule to all authorized agents, with private human blocks per user; the application serializes projection writes and verifies revision before use. Do not let arbitrary agent memory editing rewrite shared authority. [V1 block interface and concurrency warning](https://docs.letta.com/v1-sdk/memory/memory-blocks)

Archival memory uses `archival_memory_insert/search` or `client.agents.passages.insert/search`, with tags and pagination. It is retrieved on demand rather than pinned. Keep private archives separate; do not assume passages attached to one user-agent are shared just because their core block is shared. For A→B shared facts, use the canonical gateway or an explicitly shared authorized archive with source-ID reconciliation. This offers useful autonomous memory management, but adds a stateful runtime and model memory-tool behavior to test. [V1 archival interface](https://docs.letta.com/v1-sdk/memory/archival-memory)

The **current Agent SDK is a different lineage**: `system/` MemFS files are in context each turn, while other files are demand-read. Shared repositories appear as a tree rather than being inlined. [Current memory model](https://docs.letta.com/agent-sdk/memory) Its repository APIs require Cloud backend; `repositories.files.update` supports `precondition.contentSha256`, returns a commit SHA, and `files.read/list` accept a `ref`. This improves concurrency/versioning over V1 blocks, but per-file Git changes are not atomic application correction+revision+result transactions. [Current shared-repository API](https://docs.letta.com/agent-sdk/repositories)

**Adopt when:** durable autonomous assistants with editable shared playbooks are central and the pinned model/runtime/provider combination passes the same suite. **Disqualify V1 blocks as sole truth** for concurrent corrections or unbounded fleet memory. Do not combine current repository examples with legacy archival APIs into an alleged single tested SDK. Current Cloud-backed repository adoption also needs explicit infrastructure compatibility, not an assumption that local V1 hosting supplies it.

### H-Mem0: relational authority + LangGraph + scoped Mem0 adjunct

Use Mem0 for useful personal semantic recall, or separately for redacted shared operational claim retrieval. `add(messages,user_id=...,metadata=...,infer=False)` is distinct from inferred extraction; raw mode can duplicate extracted content. Current docs describe additive automatic extraction, requiring explicit update/delete for changed facts. This is useful if the application owns supersession and source receipts. [Add API and current behavior](https://docs.mem0.ai/core-concepts/memory-operations/add), [current extraction semantics](https://docs.mem0.ai/core-concepts/how-it-works)

The search adapter injects fixed entity and organization/dataset filters; perform private and shared searches separately and merge after authorization. An application's broad `agent_id` cannot stand in for a per-user private filter. Managed v3 requires entity IDs inside `filters`; SDK and product differences need pins. The current OSS source exposes `search(query, *, top_k, filters, threshold, rerank, explain, reference_date, show_expired)` but rejects non-null `reference_date` as Platform-only. It also strips identity keys from metadata; correct entity parameters must set identity. [Managed search contract](https://docs.mem0.ai/api-reference/memory/search-memories), [actual OSS source](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py)

The general search page's OSS filter table and actual current source do not describe identical breadth of operators; pin and test the selected SDK/backend rather than claiming every Platform filter works in OSS. Explicit private capsules/entity receipts remain exact application reads. Exact shared subject lookup remains canonical, so top-k/threshold misses or asynchronous admission cannot hide a plan. [Search documentation](https://docs.mem0.ai/core-concepts/memory-operations/search)

**Adopt when:** measured private paraphrase recall or extraction quality improves enough to offset extra LLM/embedding calls, index lag and scope adapters. **Disqualifier:** an integration that treats Mem0 `user_id=A` as the only location for facts B needs, or stores raw multi-user transcripts under a shared agent ID. This adjunct's correctness depends on the application gateway, not choosing a clever OR filter.

### H2: relational authority + LangGraph + gbrain shared knowledge + private application memory

Installed reference inspected read-only: package `0.42.72.1`, `src/core/operations.ts`, `docs/architecture/brains-and-sources.md`, `docs/guides/source-attribution.md`. The online main branch has reorganized operations into modules; it is not the installed revision. Neither configured host brain nor mounts/config/private memory was read.

A source organizes content inside a brain database; routing defaults are not user authorization. Current guidance specifies remote source grants and private/world filters, with a different trust boundary for local callers. A sensible hybrid uses a dedicated shared organization brain/source and application-owned private continuity, not one local personal brain with a user picker. Source-qualified identities prevent collisions and aid provenance. [Brains, sources and remote boundaries](https://github.com/garrytan/gbrain/blob/master/docs/architecture/brains-and-sources.md)

Current `remember` accepts an atomic fact, required provenance, entity/kind/validity, visibility and replacement reference; it defaults visibility to `world`. `extract_facts` defaults private; its code explicitly warns that falling back to an unqualified `remember` widens visibility. The `private` label describes local-CLI visibility, **not** arbitrary application-user-private retrieval. Pin visibility and source every time, use the application authorization boundary, and preserve our canonical claim/authority status. [Actual remember interface](https://github.com/garrytan/gbrain/blob/master/src/core/verbs.ts), [extraction and context interface](https://github.com/garrytan/gbrain/blob/master/src/core/ops/facts.ts)

`context_pack` supports budget-packed entity context, bounded entity counts and zero-LLM reads; `recall`, source-qualified pages and graph operations can complement FTS. This makes gbrain worth benchmarking for shared prose rather than dismissing it as merely another private-memory service. Still, its direct-user-always-wins attribution guidance conflicts with Q17/Q18. Replace that policy, keep ordinary disagreement visible, and validate retrieved/synthesized facts against canonical evidence and current revision. [Attribution policy requiring adaptation](https://github.com/garrytan/gbrain/blob/master/docs/guides/source-attribution.md), [operation routing](https://github.com/garrytan/gbrain/blob/master/src/core/operations.ts)

Write shared canonical claims first, then project minimal sourced statements to a fresh experiment brain through an outbox adapter. Store gbrain IDs/commit receipts and `indexed_through_revision`; reconcile canonical deltas at read time. Index only approved shared source material, not private transcripts. Treat synthesized pages as retrieval candidates with source links, not new independent evidence. Avoid a second answer-synthesis model layer unless measured useful. Subsequent isolated tests exercised actual engine exact-fact/page APIs and a controlled canonical-delta overlay; extraction, semantic retrieval, full outbox integration, remote ACLs and Gemma provider support remain untested.

**Adopt when:** paraphrased organizational questions and multi-document connections improve with the pinned service under the same evidence/privacy gates. **Disqualifiers:** default host-brain access, unresolved source grants, unpinned visibility, assumed OpenRouter extractor compatibility, or inability to prevent silent claim replacement. Rich retrieval does not remove the need for exact report joins or complete aggregates.

### H-Graph: relational authority + LangGraph + Graphiti/Zep temporal adjunct

Graphiti's actual `add_episode(name, episode_body, source_description, reference_time, source, group_id, ...)` accepts typed entity/edge hints; reads can restrict group IDs. These partitions need caller authorization; an omitted group/default is not a user boundary. Its source currently contains request-scoped driver handling to avoid concurrent group-routing mutation, illustrating why exact pinned concurrency behavior matters. [Graphiti implementation](https://github.com/getzep/graphiti/blob/main/graphiti_core/graphiti.py)

The edge model stores source episode IDs and `created_at/expired_at/valid_at/invalid_at` plus reference time. Current source distinguishes a future promise's assertion time from the promised occurrence; store a separate workover occurrence interval rather than mapping every planned end to edge invalidation. [Edge interface](https://github.com/getzep/graphiti/blob/main/graphiti_core/edges.py) The README supports JSON-object fallback for providers without reliable schema enforcement and warns structured extraction/dedup reliability varies. Our Gemma endpoint's advertised JSON capability alone cannot establish successful graph construction. [Provider and extraction limitations](https://github.com/getzep/graphiti)

**Persistent graph-fact authority versus query-time join graph:** the former stores inferred/reconciled edges that can discover cross-report relationships and changing organizational knowledge; the latter assembles verified inspection→repair→report→regulator→rule links deterministically for a question. For current Q9/Q10 the join graph has known IDs and stronger completeness. For “do similar failures share a supplier, procedure change or technician handoff?” persistent semantic edges may find relationships absent from JSON keys. Retain asserted, suspected and verified links separately; graph connectivity is not causality. Revalidate edge candidates against canonical claims/evidence and never let graph invalidation erase a domain disagreement.

**Adopt when:** held-out multi-hop prose tasks beat exact joins plus lexical/semantic retrieval with reliable citations and acceptable extraction cost. **Disqualifiers:** using extracted graph totals for the fleet, latest-edge authority replacing contested observations, or async graph state controlling correction visibility. Managed Zep and OSS Graphiti are related but not interchangeable products; the paper's service results do not establish local OSS performance.

| H-Graph: H1 + temporal Graphiti adjunct | 5 | 4 | 5 | 4 | 5 | 1 | 84.8 |

Scope scores reflect more access/index boundaries to validate, not a claim those products cannot be secured. Delivery scores include untested selected-model extraction, additional stores/runtimes and version drift. Provenance scores credit graph/source representations but do not prove extraction fidelity. LangGraph's recovery score credits documented checkpoint primitives, conditional on our idempotency tests.

The 1.6-point H1/H2 gap is too small to treat as conclusive. Moving eight weight points from delivery compatibility to prose recall reverses their order; weighting broad organizational discovery more heavily can rationally choose H2. If gbrain adds no retrieval gain on relevant cases, its richer interfaces do not justify its extra boundary. If it recovers otherwise missed correct shared knowledge with zero critical regressions, H2 should win despite being harder. All candidates fail selection if any private canary leaks, corrections fail across users, source originals disappear, or dashboards mix revisions. Weighted averages cannot compensate for these failures.

**Apply the latest model rule before this historical prior matrix.** H1's deterministic authority/FTS and no-model workflow adapters are eligible. The tested exact gbrain projection is eligible with extractor/embedding/reranker paths disabled. Mem0 vector defaults, Graphiti embedding defaults and any other-model Letta/gbrain defaults are not eligible for integration. Their documented capabilities remain useful comparison evidence, but no score overrides that restriction. A future Gemma-assisted query expansion or graph extraction path must use only Gemma and deterministic retrieval; compatibility and quality are untested.

## Papers and transfer limits

| Primary study | Useful finding/pattern | Limit for this decision |
|---|---|---|
| [MemGPT, sections 2–3](https://arxiv.org/html/2310.08560v2) | Main context, archival/recall tiers, source retention and paging make bounded context practical | Evaluated conversational/document tasks using other model generations; autonomous memory-tool success does not establish Gemma behavior, shared audience controls or correction authority. Borrow tiering; test autonomous control |
| [LongMemEval, ICLR 2025](https://arxiv.org/html/2410.10813v2) | Tests extraction, multi-session reasoning, time, updates and abstention; separates assistant-provided information | Good template for paraphrases, changed facts and “I do not have that history.” Its 500-question memory task is not a test of organization ACLs, transactional writes, full-fleet sums or atomic dashboard refresh |
| [GateMem, methods and qualitative cases](https://arxiv.org/html/2606.18829v1) | Multi-principal episodes jointly score authorized usefulness, access leakage and post-deletion recovery; hidden probes include indirect disclosure | Uses LLM-assisted synthetic episodes and structured judges, with human checks on a subset. Interface-level forgetting does not certify physical erasure. Its role-rich domains do not justify inventing team restrictions in this challenge; shared operational knowledge remains visible across teams |
| [Mem0 paper, methods/evaluation](https://arxiv.org/html/2504.19413v1) | Selective extraction and graph variants reduce retrieved context relative to full-history baselines; evaluates LoCoMo and reports token/latency measures | Used GPT-4o-mini and LLM judges; adversarial/unanswerable category was excluded. The paper's ADD/UPDATE/DELETE/NOOP algorithm differs from current additive SDK docs. No claimed percentage transfers to this app or selected model |
| [Zep temporal graph paper, sections 2 and 4](https://arxiv.org/html/2501.13956v1) | Sourced episodes, temporal edges and hybrid retrieval are a meaningful alternative to summary-only memory | Its new-edge invalidation policy prioritizes newer information, unsuitable as Q17/Q18 authority. Reported total gains coexist with worse assistant-turn recall and some weaker-model update results; DMR differences from full context are small. Hosted-service timing excludes neither product/model differences nor ingestion costs |

Paper results are evidence to test richer hybrids, not evidence that either shortlisted design has passed. The authors' [LongMemEval evaluation repository](https://github.com/xiaowu0162/LongMemEval) also makes retrieval-stage and answer-stage assessment separable; retain that separation. For this copilot, add deterministic evidence/value/scope assertions and direct inspection of pre-model context, because a plausible final answer can conceal retrieval leakage or a missing correction. No external LLM judge is necessary to verify those invariants.

GateMem's qualitative cases also show that over-restrictive retrieval can refuse a legitimate request, while an ostensibly redacted answer can still reveal the protected category. Accordingly, the local benchmark must count both cross-user shared-fact success and private-context exclusion; refusing every B request is not a pass. Add private-fact tombstone/non-recovery checks without claiming audit-row destruction, and do not let an ordinary private “forget” delete shared correction history. These are governance properties to enforce before model context construction.

## Retrieval and UI seams that affect correctness

**SQL versus semantic retrieval for causes:** begin by finding the complete well/event population with effective SQL. Join inspections to repairs by actual IDs, then follow `maintenance.report_file`; include time-overlapping shared notes where relevant. Pull applicable manual/SOP sections and overrides by type/rule IDs. Search prose to discover alternative explanations and synonyms inside that candidate universe. A report's root-cause statement is attributed evidence; a temporally adjacent repair is a possible relationship unless explicitly linked. “No recorded reason” is better than equating a stuck pump observation with a proven mechanical cause.

For Q10, enumerate every in-window spill and all linked corrective reports; extract containment delay with source span, units, relative/absolute time basis and approximation. Track `parsed | ambiguous | missing | conflicting` for each candidate. Search “contained” alone can miss “bunded,” negation, staged actions or a report saying repair took seven hours but containment took two. An LLM extractor may propose structured facts only with supporting spans; a second pass checks meaning, not just schema. Unknowns stay in a separate count/table. Regex success on templated sample reports is not proof of generalization to test data. For fleet compliance, distinguish “no recorded notice” from proof that no notice occurred.

**AG-UI versus CopilotKit:** AG-UI state snapshots/deltas provide an interoperable event substrate; sequential JSON patches and snapshot recovery help a multi-panel view. They do not supply a chart catalog, evidence viewer, durable replay or authorization policy. Keep answer-state paths allowlisted and domain payloads separate from hidden checkpoints/private tool state. [AG-UI state semantics](https://docs.ag-ui.com/concepts/state)

CopilotKit adds React chat/hooks and tool-render lifecycle components that can reduce custom frontend integration, and a registered renderer can compose several panels. This deserves a bounded comparison, rather than dismissing the shell as extra weight. The current runtime documentation states TypeScript can operate without Intelligence, while Python runtime needs Intelligence; a Python AG-UI agent can sit behind a TypeScript runtime. That is an infrastructure seam, not a reason to assume CopilotKit cannot fit. [Runtime architecture](https://docs.copilotkit.ai/backend/copilot-runtime), [tool renderer API](https://docs.copilotkit.ai/reference/hooks/useRenderToolCall)

Latest user steering makes rich enterprise UI the priority: treat **CopilotKit + AG-UI with a free open-source enterprise component catalog**, and an A2UI composition variant, as preferred candidates to validate. Direct AG-UI is the baseline, not the default winner for having fewer dependencies. Test composable panels, table/filter interactions, accessible responsive behavior and evidence drill-down using actual components/catalog integration; the UI track owns those results. This review's consistency/authority contracts apply equally to each shell.

For both paths use the same one-answer `blocks[]` contract, trusted component catalog and result/evidence IDs. A correction receipt drives a knowledge event; this is not itself a data patch authorized to edit arbitrary client state. Stage all affected R+1 panels and narrative, validate, then publish one answer-version swap. Never update the headline to 5.4 bbl while a chart and compliance card still use 4.5. Every panel exposes its evidence/time/revision through a shared source viewer; population coverage and disputed claims belong in the narrative too, not only tooltips. UI framework choice cannot repair bad provenance.

### Counterexamples to H1 and the deciding measurements

Plausible failure: A says “after the turnaround, the older pump units in the western pads need a second look,” with the equipment generation and turnaround relationship distributed across earlier shared notes. B asks “which locations need the post-turnaround follow-up?” H1's exact ID joins plus FTS can miss the paraphrase, and a rigid subject classifier may fail to attach the claim to every affected well. H2's sourced entity cards/semantic recall or Graphiti's persisted relationships could recover it. Preserve the original uncertainty and scope rather than fabricating a complete affected fleet.

Deciding test: create held-out shared mini-corpora with ground-truth source spans, indirect equipment/team references, synonym-rich queries, temporal updates and distracting namesakes. Freeze the same canonical claims and per-query evidence budget for H1/H2; compare source recall, correct scope, evidence-supported answer quality, and extraction/index cost. Add one variant requiring automatic extraction to expose write-path errors separately. If H2 improves correct shared retrieval materially without a critical regression and within latency/model budget, adopt H2. This is an appropriate reason to accept greater complexity.

A second counterexample is operational: LangGraph can add checkpoint serialization, adapter quirks and duplicate internal state without improving a short two-call request. Compare it to the plain journal control under forced interruption after each external side effect. If the plain control restores the same receipts/panels with less integration code and fewer faults, its lower framework count is a measured advantage, not an assumed virtue.

## Same-fixture isolated experiment plan

The live recovery dispatch expanded this worker's ownership to the assigned memory experiment worktrees and `memory-experiments.md`. The measured subset is complete there; the wider semantic/model evaluation remains an unexecuted proposal subject to the latest Gemma-only constraint. Root retains main application and final integration ownership. All stores used here were fresh synthetic stores; no configured personal gbrain or private memory was accessed.

**Compare H1 and H2 first**, with the plain journal as a workflow control where practical. Same importer, immutable sources, typed ledger, authorization, output schema, model endpoint/settings, prompt/evidence budget and test fixture definitions. H2 adds only a shared gbrain projection/retrieval adapter; it cannot win by seeing private histories or a larger evidence budget. Record pins, commits, extractor/embedding configuration, every model call including background work, retries, prompts/outputs and store/index watermarks.

Separate three experiment levels:

1. **Deterministic seam tests, no model:** shared A→B save/read with index disabled/stale; private canary isolation; exact entity receipt; formal correction/rule scope; duplicate delivery; concurrent same/different targets; crash after commit before checkpoint; restart and replay; dataset append; mid-dashboard revision. These establish storage/workflow properties only.
2. **Recorded-plan/extraction fixture replay:** feed identical validated candidate drafts/view plans to each adapter. Inject negation, dates, uncertain subjects, conflicting values and source-span mismatches. Establish admission/supersession behavior without confusing LLM variability with storage behavior.
3. **Future authorized live-model trials:** both systems use the coordinator-verified Gemma endpoint for the same prompts; other models/encoders/rerankers are excluded. Evaluate cold/warm context and index lag; repeat matched trials where rate limits permit and report unavailable runs. Do not claim live extraction/semantic quality from deterministic stubs. No live calls were made in this review.

Proposed initial suite: 12 scenario families above with 3 paraphrase/order variants each; all 18 official scenarios separately; held-out new IDs/names/report phrasing. Add at least 10 semantic relationship/organizational cases so H2's potential benefit is actually tested, rather than selecting a suite only exact SQL can win. Keep a small tune set separate from held-out queries. For small samples report counts and paired outcomes, not a spurious statistical victory.

Measure: exact effective values/units/windows; shared fact recall at canonical-ID and source-span level; private pre-model leakage; abstention; conflict retention; rule scope; correction read-after-write lag; complete evidence coverage; replay duplicate side effects; memory budget/omitted categories; panel revision agreement; time to first useful panel/final answer; p50/p95 only with enough observations; extraction and indexing latency; all model/embedding calls, usage and actual cost. Use deterministic assertions for known values/IDs/scope and human evidence review for paraphrase/explanations; any optional judge score is supplementary.

**Hard gates:** zero private-canary exposure anywhere in B's context, exact correction propagation for all specified fixtures, originals/audit preserved, no duplicate write after retry, no mixed dashboard revision, no unsupported source accepted as fact. A “not enough evidence” outcome can pass honesty while failing completeness; report those dimensions separately. Require every critical gate before comparing mean quality. H2 promotion criterion is proposed: at least 10 percentage-point absolute gain on held-out shared semantic source recall or at least 3 additional fully evidenced successes, no critical regression, and agreed acceptable end-to-end latency/call budget. The small-set threshold is a review rule, not a statistical claim; expand matched trials when outcomes are close. Admit a tie if evidence cannot distinguish them.
