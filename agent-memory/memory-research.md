## Recommendation and decision

Build a bounded Q&A workflow in `backend/chains/` with application-owned durable memory and a shared append-only knowledge ledger. Use exact typed tools for records, calculations and report/rule evidence. Give the model a small read-only core, an **always-loaded durable static-fact capsule for the active user**, a rolling private summary, recent exchanges and selectively retrieved archival memories. Keep formal corrections and type rules in structured shared storage that every calculation and visual reads; never rely on the model remembering to retrieve a correction. Start with the retrieval track's relational store and avoid a separate memory service for the hackathon.

Use **3,000 loaded memory tokens by default**, and evaluate 5,000 against the same fixtures before increasing it. These caps exclude the current request, tool schemas and fresh query evidence. Preserve the entire private archive separately. The value is a tunable engineering starting point, not a published optimum. One targeted private lookup can recover a missing entity set without loading every past discussion.

This combines useful patterns from LangGraph's thread state and cross-thread namespaces, Letta/MemGPT's in-context versus archival tiers, Mem0's selective fact extraction, and gbrain's sourced entity knowledge. Frameworks do not supply this project's correction authority or privacy policy automatically. LangGraph documents thread checkpoints separately from namespace-based durable stores; namespaces organize data and still need application authorization. [LangGraph memory concepts](https://docs.langchain.com/oss/python/concepts/memory)

**Choose alternatives only for demonstrated need:** LangGraph when resumable graph steps and interruptions outweigh extra framework setup; Letta when autonomous stateful agents and memory editing are the product; Mem0 when private semantic fact recall dominates; gbrain when a broader sourced organizational knowledge system is already a supported dependency. None replaces the effective-record layer.

## Exact memory model and scope

| Layer | Durable content | Scope and prompt behavior | Authority |
|---|---|---|---|
| Read-only core | Specialist persona, scope/uncertainty rules, memory routing; directory-backed active user display identity | Small, always loaded for active user | Behavioral configuration only; no mutable asset truth |
| Durable static-fact capsule | Explicitly remembered stable personal/work facts and preferences; confirmed useful extracted static facts; compact source/manifest IDs | Per user across sessions; **always loaded**, with version and bounded compaction | Attributed private facts; distinct from conversational summary and shared asset truth |
| Recent exchanges | User input and final validated response, stable message/exchange IDs, tool run references | `(dataset_namespace, user_id, thread_id)`; recent raw projection | Historical conversation, never current asset evidence |
| Rolling summary | Goals, resolved references, unresolved questions, source message ranges, selected entity-set IDs, corrections/rules pointers | Same private thread; <=700 tokens | Lossy navigation aid; recover source on demand |
| Private semantic memory | Explicit remembered preferences/static facts; extracted useful facts with source messages and confidence label | `(dataset_namespace, user_id)` across sessions; relevant retrieval | Attributed personal/contextual information |
| Private episodic/entity memory | Ordered entity IDs from a validated answer, question intent/date/window, answer/run ID, authoring user, timestamps | Same user across sessions; exact lookup before semantic fallback | Authoritative for what the user discussed, not for current measurements |
| Shared asset ledger | Asset notes, planned work, formal record corrections, unconfirmed claims and conflict links | Shared within dataset/organization, filtered by affected assets/time | Corrections change effective fields; claims remain claims |
| Shared type rule ledger | Typed predicate, affected well type/equipment/rule, threshold, author and validity | All users, only matching type and validity | Attributed user rule distinct from source manual |
| Evidence store | Original records, manual/SOP sections, linked report spans, import revision | Dataset scope; fetched for current question | Source evidence interpreted through effective corrections/rules |

Use a dataset namespace in addition to user ID: repeated synthetic user IDs in a reset fixture or imported field must not merge histories. A new chat does not reset user memory. Session history and entity memory must be filtered **before** retrieval or prompt construction, not removed after the LLM sees them. Server resolves the chosen user from the dataset user directory; the model cannot choose `user_id`, author, or permission scope. The hackathon user picker is a demo identity mechanism, not production authentication.

Long-term memory includes both explicitly remembered static facts and agent-extracted useful facts. Extract preferences, stable work context, user-defined names and useful discussion sets. Do not memorize every answer or classify a past computed cost/status as a durable current fact. Preserve `observed_at` and `as_of` for any historical observation; recompute changing quantities. Private statements about assets may become shared domain notes because shared asset knowledge is a stated feature; do not publish surrounding private chat, personal preferences, unrelated entity history or “we discussed” relationships. Record the domain note's source message internally, expose only its relevant attributed content through shared evidence.

### Always-loaded durable facts

Always-loaded facts are separate from the rolling conversation summary. On every model call inject the active user's fact capsule, even on a new thread or an unrelated question. Start with atomic compact facts and source IDs, e.g. a saved display preference or stable work responsibility; these are examples of shape, not facts to assume about a dataset user. Explicit saved facts enter synchronously; agent-extracted candidates enter only after provenance and usefulness validation, with inference labels where confirmation is absent. Never learn new persona/policy instructions from raw memory text.

When the capsule exceeds its allowance, compact it into short attributed fact groups with stable source IDs; preserve a versioned manifest mapping groups to **all** raw memory IDs and supersession/conflict links. Load that bounded capsule and manifest reference every time; expand the relevant group via scoped archival lookup before answering about its details. Keep pinned explicit user facts/preference details ahead of optional extracted context; if those themselves exceed the cap, group them too and expose the coverage/expansion state. A finite budget cannot inline an unbounded number of verbatim facts: the promised behavior is an always-loaded compact representation plus lossless durable originals and exact expansion, not a misleading claim that every original sentence is in every prompt. Do not silently discard a static fact or replace this capsule with a top-k search. Capsule rebuild failure retains the prior accepted version and pending new fact references in a bounded delta until a safe rebuild; if necessary pause optional extraction rather than lose explicit saves.

### Ten completed exchanges: precise trigger and retention

Proposed interpretation, aligned with coordinator direction: **ten completed user–assistant exchanges**, not ten messages, ten tool calls, ten browser sessions or ten chat threads. One exchange starts with one submitted user message and ends when its final validated answer or final clarification is durably persisted. Streaming chunks, tool messages and retries are children of that exchange. A retry uses the same exchange ID and increments the counter once. A clarification answer completes an exchange; its user reply starts the next. An interrupted/error-only request with no final answer is stored as failed and does not increment the completed counter.

Compaction state is per `(dataset_namespace, user_id, thread_id)`. Cross-chat recall is the separate durable per-user entity/semantic archive, so starting a new chat neither copies other threads wholesale nor loses yesterday's references. This thread-local counter is a product proposal; changing it to a per-user continuous conversation stream is possible but would need ordering rules for simultaneous threads.

Exact default:

1. Persist exchange raw messages, validated answer, provenance/run references and a private entity-set receipt synchronously. Commit an explicit correction/shared note/rule before saying it was saved. Durable useful private facts that the user explicitly asks to remember also commit on this path; optional inferred facts can be extracted asynchronously.
2. After successful exchange `10, 20, 30, …`, enqueue exactly one compaction job keyed by `(thread, completed_batch_number)`. Schedule overflow compaction separately; it does not reset the ten-exchange counter. Failed calls and retries cannot schedule duplicate logical jobs.
3. At trigger N, the new summary covers completed exchanges `1..N-3`, preserving the newest **three** completed exchanges as the recent tail. At N=10 summarize 1–7; at N=20 summarize 1–17 and retain 18–20. Load their raw text when it fits; for large dashboard responses load compact answer/entity receipts while the full raw exchanges remain durable. Between triggers carry the prior summary plus its not-yet-covered raw tail, subject to the token guard. Thus there may be up to twelve raw tail exchanges just before the next trigger; the count is not a promise to load twelve large answers.
4. Summary input is the prior accepted summary, newly covered source exchanges, and structured entity/correction/conflict pointers. Do not feed current numerical values as timeless truth. Validate coverage watermark, owner identity, source references, unresolved questions and preserved referenced entity sets. Keep full IDs in structured sidecars; prose may omit them only if the sidecar points to exact records.
5. Store `summary_version`, covered range, source hashes, prompt/model version and creation time. Use compare-and-swap on the previous summary version/coverage so parallel jobs cannot overwrite newer state. Publish atomically. The durable original transcript and entity receipts remain intact; compaction changes prompt loading only.
6. If summarization is late or fails, keep the previous summary and raw archive, mark the job pending/failed and do not claim completion. The next prompt uses a deterministic compact receipt projection and exact retrieval where needed; never silently drop a correction or borrow another user's history. Retry at most once per job during the demo; surface operational failure in trace, not as fabricated memory.

Default archival retention proposal: retain all private transcript and entity receipts for the hackathon dataset/run until explicit reset/deletion; do not expire yesterday's discussion by a short TTL. Summaries remain versioned and rebuildable. Production retention/deletion policy is an open product decision, not an assumed indefinite legal requirement. User deletion must cover summaries, entity receipts, embeddings, caches and derived memory; raw shared domain corrections need a separately defined audit-retention policy rather than a casual chat “forget” deleting fleet truth.

### Token guard and 3K versus 5K

| Loaded-memory allocation (hard maximum) | 3K default | 5K trial |
|---|---:|---:|
| Read-only persona/routing + active identity | 500 | 500 |
| Always-loaded durable static-fact capsule | 800 | 1,000 |
| Rolling private summary, including compact reference sidecar | 700 | 700 |
| Recent raw exchanges / compact answer receipts | 600 | 1,400 |
| Relevant private archival facts and entity-set references | 400 | 1,400 |
| Total | 3,000 | 5,000 |

These are **total loaded-memory** caps, not long-term-only caps: durable capsule plus selected archival loading is 1,200 tokens in the 3K policy and 2,400 in the 5K trial. If the user later chooses 3K or 5K for long-term memory alone, add core/summary/recent allowances separately and remeasure the larger full prompt. Total archive size is independent of either policy.

Unused allowance can move between recent/archive buckets, never above the total; core, capsule and summary can be smaller. Count the complete serialized context, including JSON keys and citation metadata, using a compatible tokenizer where available; label approximate estimates and apply a safety margin otherwise. Shared effective facts and current cited evidence have a separate query-evidence budget: they cannot disappear because private history filled its cap. Never count a huge hidden UI payload as “free” context.

Before **every** model call, enforce `instructions + tool schemas + memory + current input + evidence + reserved output + safety <= verified endpoint context limit`, counting each serialized segment once (persona/core belongs to the memory allocation, not twice). Initial operational input ceiling proposal: 16K tokens even if the advertised model window is much larger; reserve 2K output and 1K margin separately. This is tunable after actual traces. Trigger an early summary when memory exceeds its cap or overall input exceeds the ceiling, even before exchange ten. Preserve the newest user message; retrieve large payloads by IDs, page rows, and use compact typed tool receipts instead of replaying all previous chart data. Never split tool-call/result pairs in an API message sequence. If one user input or indispensable source set cannot fit, narrow/page the request explicitly rather than silently truncating it.

Eviction order: duplicate snippets → old rendered payloads replaced by run/entity references → irrelevant private archival memories → oldest raw exchanges summarized. Relevant correction/conflict/type-rule pointers must survive, but effective values still come from tools; paginate/chunk evidence when indispensable provenance itself exceeds the budget. A 5K budget adds up to 2,000 input tokens per generation call, or up to 4,000 for a two-call plan/compose exchange if both use it. In 100 such exchanges that is up to 400K additional input tokens, before cache effects. At an illustrative paid rate P dollars per million input tokens, that is `0.4 × P`; actual selected endpoint price/usage must be recorded rather than inferred.

Evaluate paired 3K/5K runs with identical model/settings/data/seeds where supported: Q11/Q16 entity recall, paraphrases, multi-day references, conflicts, overflow and distractors. Promote 5K only for reproducible recall gains without factual/privacy regression and acceptable p95 latency/request consumption. Do not optimize token count at the expense of losing IDs; exact structured entity receipts should make the smaller budget competitive.

## Deduplication, conflicts, TTL and supersession

Every durable memory has: memory ID, dataset namespace, scope/owner, kind, subject IDs, predicate, normalized value/unit where applicable, source message/record/span, author, recorded time, valid time, extraction method/version, status and supersedes/conflicts links. `valid_from/valid_to` describes the world; `recorded_at` says when the system learned it. Do not use the machine date for a scenario's “today.” Keep an explicit query reference date and UTC bounds, with timezone for interpreting “yesterday.” Q6 must use its explicit 16 Jun–16 Oct 2026 window.

Keep **data reference time** separate from **knowledge snapshot**. A correction learned on 17 Oct can correct a 15 Oct inspection used by a scenario whose reference date is 16 Oct: target the inspection field, do not require its observation time to fall after correction receipt. Ordinary questions use the latest accepted knowledge revision with the stated data window. Only an explicit “what did we know then?” request limits recorded/transaction time. An RCA override effective “now” changes eligibility evaluated now over the whole stated lookback; it does not count only repairs occurring after the override was recorded. If the user gives no precise override validity, propose `valid_from = active query reference date`, open end until superseded, mark that assumption in the receipt and preserve `recorded_at` separately. Never retrofit a changed safety threshold to unrelated historical applicability without an explicit rule scope.

Dedup inside scope only. Normalize units and canonical entity IDs; exact duplicates can combine source references without discarding authors. A similarity match is a candidate, not permission to merge opposite values. Distinct time intervals or different inspection IDs are different facts. Repeated delivery of the same message uses an idempotency key. Avoid global content-hash keys that let identical text join private records across users.

For corrections, store original value, previous effective value, proposed/effective new value, source record ID and field, author, timestamp, reason (nullable with `not_supplied`, never invented), scope, validity, revision and transaction ID. A repeated identical correction adds provenance/idempotent receipt; competing corrections to the same field/interval preserve both. When an explicit correction clearly supersedes an earlier correction, link it; otherwise flag a correction conflict and request reconciliation rather than choose by user seniority or timestamp alone. The existing accepted effective value can remain active with conflict disclosed while resolution is pending. The scenario's clear first correction applies immediately even when an ordinary inspector note disagrees: Q12 asks for confirmation of the disagreement, not a gate that blocks the correction.

Precedence is typed, not a universal source-ranking list: apply accepted formal field corrections; evaluate the applicable manual plus valid scoped user overrides; preserve all claims and contradictory evidence; use effective observations for status; treat the summary solely as navigation. An ordinary `operator_note` or `operator_feedback` is never promoted to a field correction just because it sounds confident. An explicit “note for all T350 wells” rule can be a structured user override if target rule/equipment/window are unambiguous. It does not change T200, rewrite the manual, or apply to unrelated equipment.

TTL means retrieval eligibility, not erasure. Explicit dated plans expire as active plans at their end; retain them historically and do not infer completed work or a restart. A ten-day plan starting 17 Oct can be represented as `[17 Oct, 27 Oct)` with “about ten days,” pending precise times. Static personal facts/preferences have no automatic expiry; add review metadata if needed. Inferred preferences can have a configurable 90-day review date, not automatic truth or deletion. Corrections and type overrides have no silent TTL; only explicit validity/supersession changes applicability. Unconfirmed claims remain attributable even when old; they do not become confirmed through repetition. Mem0's documented expiration similarly hides expired memories from ordinary retrieval while preserving ID lookup; our ledger still needs its own as-of rules. [Mem0 expiration](https://docs.mem0.ai/platform/features/memory-expiration)

## Interface contracts for retrieval, UI and chains

Names below describe proposed interfaces, not implemented APIs. Align canonical names with the retrieval/UI reports before implementation. Use `EvidenceRef`, `ResultSet`, `dataset_revision`, `knowledge_revision` consistently across tracks; never fork a second independent data payload for narration and visuals.

**Request context:** trusted `dataset_namespace`, `user_id`, `thread_id`, `exchange_id`, request ID, explicit `reference_date`, timezone, normalized date bounds and `minimum_knowledge_revision`. Scope/author never come from model-produced JSON. Check thread ownership on read, write, resume, streaming and reconnect. Cache keys include dataset revision, knowledge revision, user scope, normalized query/bounds and tool/prompt versions.

**Private memory interface:** `load_memory(context, query, entity_hints, token_budget)` → core, always-loaded static-fact capsule/version/manifest ref, accepted summary/coverage, recent exchange projections, relevant archival fact refs, exact entity sets, token counts and omitted categories. `resolve_private_reference(context, phrase, time_hint)` → one or more candidate entity sets with ordered IDs, source exchange/run, timestamp/timezone and resolution status `resolved | ambiguous | absent`. Search user's exact entity receipts by dates/intent first, then scoped lexical/semantic archive. When ambiguous, clarify; when absent for Jessica, say absent rather than search Michael's history. Return an explicit empty scope when no memories exist.

**Shared write interface:** `propose_knowledge_change(context, target, kind, value, reason, validity)` → typed draft and conflict findings; `commit_knowledge_change(validated_draft, expected_revision, idempotency_key)` → durable receipt, new revision, old/effective values, affected subjects/rules, and invalidation event. Clear corrections in Q12/Q13 and explicit scoped Q14 rules are authorized user intent; do not add a generic approval dialog. Ask only for missing target/field/meaning or unresolved conflicts. Ordinary claims are committed as attributed unconfirmed claims with no raw-field mutation. Store the minimal shared domain statement, never the whole private transcript.

**Retrieval/domain tools:** require bounded typed arguments and return exact `ResultSet` tables with schema, units, date semantics, coverage/completeness, dataset/knowledge revision, formula/rule refs, source records and warnings. Suggested capabilities: latest effective well status; filtered fleet status; temperature series; spill events/classes; downtime ranking; maintenance costs; equipment corrective counts and RCA eligibility; linked report/SOP retrieval; compliance timelines; shared claims/conflicts; record/rule details. Domain SQL/filters run server-side over the full relevant dataset. Do not give the model arbitrary SQL or use top-k memory search to compute totals. Report-only facts must be fetched by `maintenance.report_file` and verified spans.

**EvidenceRef:** align retrieval's `evidence_id`, `source_kind`, `source_id`, dataset/file revision, safe relative `path` or viewer link, record ID/JSONL line and JSON pointer or Markdown section/byte range, content hash, author/time when relevant, original/effective distinction and correction/rule IDs. The server resolves the evidence ID; model-supplied paths are never arbitrary filesystem-read arguments. Private reference provenance is viewable only by its owner. Shared correction provenance exposes the domain correction and author, without granting access to the original private chat.

**Answer/UI envelope (`AnswerEnvelope`):** message/run/exchange ID, reference date/window, dataset/knowledge revision, concise narrative with `fact | inference | suggested_check` claim labels and evidence refs, `blocks[]`, data refs to immutable `ResultSet`s, uncertainty/conflict flags and optional saved-memory receipts. Each block has a stable ID, allowed component type, title, data ref/encoding and evidence refs. The UI track owns the final renderer schema; model output selects approved components and dataset columns, never executable React. Component repair cannot change tool facts. A strict JSON schema claim is conditional on endpoint support; local parsing/validation remains required.

**Events:** `status` (e.g. “Checking the latest readings and any corrections”), `tool_started`, `tool_result`, `block_validated`, `answer_complete`, `error`, and `knowledge_changed`. Emit only validated factual panels. On a shared correction commit, atomically increment `knowledge_revision`, invalidate dependent query/answer/visual caches and notify active clients. A result in flight uses one consistent snapshot; if the revision advances before publication, rerun affected tools or label it historical and offer refresh. For later questions require at least the committed revision so Q15 cannot read a stale replica/cache. Already-open historical messages retain their as-of label; a refreshed visual must not reuse a stale narrative.

**Repair boundaries:** maximum one model formatting repair per stage; allowlisted tool/field/ID validation before execution; no evidence invention or “fixing” a tool number; one bounded replan after actionable missing tool context, then honest partial/failed answer. Writes have their own transaction/idempotency policy and must never be retried by the generic text-repair path. Store tool outputs and shared commit receipts before generation so a network retry cannot apply the correction twice.

## Persona and example answer

Separate a measured fact, a plausible interpretation and a useful next check; do not blend them in confident prose. Say “No recorded reason” when that is what the evidence supports. Use names from the directory for people/areas/teams and well IDs for assets. Ask one focused confirmation when a claim conflicts; avoid robotic disclaimers and repetitive greetings. Never imply real inspection access, live telemetry, a repair action or regulatory submission that the tools did not perform.
